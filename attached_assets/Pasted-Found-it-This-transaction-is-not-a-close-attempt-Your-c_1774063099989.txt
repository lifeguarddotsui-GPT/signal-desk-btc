What to fix now

1. Split open and close builders completely

Do not let closePosition() share the same transaction assembly path as openPosition().

You need two separate codepaths:

buildOpenOrderTx(...)
buildClosePositionTx(...)

Not:

buildTradingOrderTx(mode)

unless mode is guaranteed to dispatch to distinct Move calls.

⸻

2. Add a hard assertion before signing

Before executing a close, inspect the built PTB.

If any command includes create_trading_order, abort locally.

Example:

function assertNoCreateTradingOrderInClose(txSummary: string[]) {
  const bad = txSummary.find(x => x.includes("create_trading_order"));
  if (bad) {
    throw new Error("Close flow incorrectly built create_trading_order transaction");
  }
}

Even simpler: log the final Move calls before submit.

⸻

3. Your close flow must call the actual close/settle Move function

Right now it does not.

You need to identify the Typus function that truly closes or settles an existing position. Whatever that function is, the final command must be that function, not create_trading_order.

So your logging for every close attempt should show:

logger.info("CLOSE_TX_COMMANDS", commands);

and you should verify the final command is the expected close method.

⸻

4. Handle linked orders first

The abort name is very explicit:

too_many_linked_orders

So before any new order-like action, you need:
	•	fetch linked orders for the position/account
	•	cancel stale linked orders
	•	wait for confirmation
	•	refresh state
	•	only then proceed

But again, that only helps if the next tx is a true close call.

⸻

5. Stop using order creation as a proxy for close

If your current logic is trying to flatten by placing an opposite order, that is likely what’s creating the linked-order pileup.

That may work on some venues, but here it is clearly breaking on Typus.

You need:
	•	either true protocol-native close/settle
	•	or a very explicit “reduce-only flatten” flow with cleanup and linked-order limits enforced

At the moment, it is neither clean nor safe.
