Below is the full implementation plan for Blue Water’s real-time portfolio system.

The goal is not just “faster refresh.” The goal is to make the UI reflect a single coherent truth even when Typus, keeper settlement, wallet balances, and transaction confirmations arrive at different times.

1. System objective

Build a backend-driven portfolio state engine that:
	•	tracks agent and user portfolio state as a canonical source of truth
	•	tracks orders, positions, and settlement separately
	•	streams updates to frontend in near real time
	•	uses Blue / Yellow / Green as meaningful confidence states, not just visual decoration
	•	reconciles constantly against chain and Typus data
	•	gracefully handles lag, partial fills, close latency, settlement latency, and stale RPC reads

⸻

2. Main design principle

Frontend should render state, not invent it

Right now the frontend is likely doing too much of this:
	•	fetch wallet balance
	•	fetch agent balance
	•	fetch Typus position state
	•	fetch backend status
	•	combine it locally
	•	hope timestamps line up

That creates race conditions.

Instead:
	•	backend builds canonical state
	•	frontend fetches one snapshot
	•	frontend subscribes to websocket delta updates
	•	frontend only renders what backend says is true

This is the most important architectural change.

⸻

3. Core concepts

You need to separate these four things:

A. Wallet balances

Actual confirmed SUI in wallets:
	•	user wallet
	•	agent funding wallet
	•	savings/reward wallet

B. Orders

Intent to open/close that may or may not be filled yet:
	•	open submitted
	•	accepted
	•	partially filled
	•	canceled
	•	close requested

C. Positions

Live market exposure:
	•	long/short
	•	size
	•	entry
	•	margin
	•	mark price
	•	unrealized PnL
	•	liquidation context
	•	state: opening/open/closing/settling/closed

D. Settlement

Value that should return but has not yet returned:
	•	pending margin return
	•	pending realized pnl
	•	pending fees
	•	keeper settlement in transit

This separation fixes most of the confusion.

⸻

4. Improved Blue / Yellow / Green semantics

Your current semantic idea is good. It just needs strict rules.

Blue = Estimated

Use blue when the displayed number is economically meaningful but not fully confirmed.

Examples:
	•	mark-price-based portfolio estimate
	•	position known, wallet not yet updated
	•	order believed filled but final Typus account snapshot not yet confirmed
	•	close estimated from backend + tx receipt but keeper settlement not finalized

Blue means:

“This is our best live estimate of your value.”

Yellow = Pending transition

Use yellow when state is actively changing and the number is unstable due to a lifecycle event.

Examples:
	•	tx submitted
	•	order accepted but not yet fully reflected
	•	close requested
	•	position transitioning from open to settling
	•	settlement expected but not landed
	•	reconciliation mismatch in progress

Yellow means:

“A state transition is in progress. Value is moving.”

Green = Verified

Use green only when relevant sources agree and no active transition is unresolved.

Examples:
	•	wallet balance confirmed
	•	open positions confirmed
	•	no unaccounted pending settlement
	•	backend portfolio engine and reconciliation pass agree within threshold

Green means:

“This number is fully verified.”

Suggested UI rule

For any displayed value, attach:
	•	confidence: blue / yellow / green
	•	reason: short code like pending_close, mark_estimate, verified_chain
	•	updatedAt
	•	optional stale flag

That makes color tied to real system logic.

5. Backend topology

Recommended backend services:

5.1 Portfolio Engine

The canonical state reducer.

Responsibilities:
	•	maintain per-agent and per-user portfolio state
	•	apply incoming events
	•	compute portfolio values
	•	assign confidence color
	•	expose snapshot API
	•	publish updates to websocket

5.2 Transaction Tracker

Tracks all submitted txs from Blue Water.

Responsibilities:
	•	store tx digest
	•	agentId / userId / action mapping
	•	confirmation state
	•	failure state
	•	timing metrics
	•	emit tx lifecycle events

5.3 Typus Sync Service

Tracks positions and orders from Typus.

Responsibilities:
	•	fetch open positions
	•	fetch open orders
	•	fetch account margin
	•	fetch fill/close status when possible
	•	update mark-price-based unrealized pnl
	•	emit order/position events

5.4 Wallet Sync Service

Tracks all relevant wallet balances.

Responsibilities:
	•	funding wallet balances
	•	savings wallet balances
	•	user wallet balances if displayed in app
	•	detect settlement arrival
	•	emit wallet delta events

5.5 Reconciliation Service

Compares expected state against observed reality.

Responsibilities:
	•	compare state engine vs Typus vs wallet snapshots
	•	correct drift
	•	emit warnings / corrections
	•	flag stale data

5.6 Broadcast Service

Pushes state to clients.

Responsibilities:
	•	websocket / SSE fanout
	•	channel subscriptions
	•	sequence numbers
	•	resend policy
	•	latest snapshot cache

5.7 Market Data Service

Tracks live prices used for unrealized pnl.

Responsibilities:
	•	mark price refresh
	•	price freshness
	•	event emission for price-driven changes

7. Portfolio formula

Do not use raw wallet balance alone.

Agent total portfolio value

confirmedFundingBalance
+ confirmedSavingsBalance
+ investedMargin
+ unrealizedPnl
+ pendingSettlementAmount
+ pendingMarginReturn
- pendingFees
- pendingOrderReserve?   (depends on whether reserve is already excluded from funding balance)

You must define this carefully depending on how Typus reserves margin.

Recommended accounting rule

If reserved margin is already deducted from wallet balance, do not subtract it again.

Use one accounting convention only:
	•	either balance is gross and reserve is subtracted
	•	or balance is net and reserve is informational only

Do not mix both.

9. State reducer design

Your state engine should process events in order and update state.

Example reducer outline

function reduceAgentState(
  state: AgentPortfolioState,
  event: PortfolioEvent
): AgentPortfolioState {
  switch (event.type) {
    case 'ORDER_SUBMITTED':
      return recalc({
        ...state,
        openOrders: [...state.openOrders, event.order],
        pendingOrderReserve: state.pendingOrderReserve + event.order.collateralReserved,
        confidence: makeConfidence('yellow', 'pending_open'),
      });

    case 'ORDER_FILLED':
      return recalc({
        ...state,
        openOrders: markOrderFilled(state.openOrders, event.orderId),
        pendingOrderReserve: Math.max(0, state.pendingOrderReserve - event.marginUsed),
        confidence: makeConfidence('blue', 'mark_estimate'),
      });

    case 'POSITION_OPENED':
      return recalc({
        ...state,
        openPositions: upsertPosition(state.openPositions, event.position),
        investedMargin: state.investedMargin + event.position.marginUsed,
        confidence: makeConfidence('blue', 'mark_estimate'),
      });

    case 'POSITION_CLOSE_REQUESTED':
      return recalc({
        ...state,
        openPositions: updatePositionState(state.openPositions, event.positionId, 'closing'),
        confidence: makeConfidence('yellow', 'pending_close'),
      });

    case 'POSITION_CLOSED':
      return recalc({
        ...state,
        openPositions: removePosition(state.openPositions, event.positionId),
        settlingPositions: [...state.settlingPositions, event.position],
        investedMargin: Math.max(0, state.investedMargin - event.position.marginUsed),
        pendingSettlementAmount:
          state.pendingSettlementAmount + event.expectedSettlement,
        confidence: makeConfidence('yellow', 'pending_settlement'),
      });

    case 'SETTLEMENT_CONFIRMED':
      return recalc({
        ...state,
        confirmedFundingBalance: event.newFundingBalance,
        pendingSettlementAmount: Math.max(0, state.pendingSettlementAmount - event.amount),
        settlingPositions: removeSettledPosition(state.settlingPositions, event.positionId),
        confidence: makeConfidence('green', 'verified_chain'),
      });

    case 'MARK_PRICE_UPDATED':
      return recalc({
        ...state,
        openPositions: updateMarkPrices(state.openPositions, event.prices),
        confidence: state.openPositions.length
          ? makeConfidence('blue', 'mark_estimate')
          : state.confidence,
      });

    case 'RECONCILIATION_CORRECTED':
      return recalc({
        ...event.correctedState,
        confidence: makeConfidence('green', 'verified_reconciled'),
      });

    default:
      return state;
  }
}

The recalc() function should:
	•	recompute total portfolio value
	•	update aggregate pnl
	•	bump sequence
	•	stamp updatedAt
	•	check stale thresholds

10. Order tracking and position tracking must be separate

This was one of the strongest ideas and it is essential.

Why separate them

Because these are not the same thing:

Order

A request or instruction in the market system

Position

An active exposure after fills occur

Settlement

A post-close financial return process

If you mix them, the UI gets confused:
	•	“0 positions open” but value still missing
	•	“wallet low” but order reserve is active
	•	“position closed” but funds not returned yet

Recommended UI buckets

For each agent show:

Open Orders
	•	order state
	•	requested size
	•	filled size
	•	reserved collateral

Open Positions
	•	market
	•	side
	•	size
	•	entry
	•	mark
	•	uPnL
	•	margin used

Settling
	•	recently closed positions
	•	expected settlement amount
	•	settlement age
	•	keeper pending indicator

Wallets
	•	confirmed funding balance
	•	confirmed savings balance

That makes the app much more legible.

11. Synchronization cadence

Not everything should refresh on the same interval.

11.1 Hot loop: 1–2s

Used for:
	•	mark prices
	•	unrealized pnl recomputation
	•	active open position state refresh for currently running agents

11.2 Warm loop: 3–5s

Used for:
	•	Typus position snapshots
	•	order snapshots
	•	agent-level activity sync

11.3 Slow loop: 10–20s

Used for:
	•	confirmed wallet balance refresh
	•	full reconciliation
	•	stale state audit

11.4 Immediate event-triggered refresh

Trigger instantly after:
	•	order submit
	•	close submit
	•	tx confirmation
	•	Typus account change
	•	detected settlement arrival

This hybrid model is much better than blind polling.

15. Reconciliation engine

This is what keeps truth honest.

Reconciliation formula

Every 10–20 seconds, compute:

expected =
confirmedFundingBalance
+ confirmedSavingsBalance
+ investedMargin
+ unrealizedPnl
+ pendingSettlementAmount
- pendingFees

Compare against:
	•	latest Typus account state
	•	latest chain wallet balances
	•	backend internal state

Drift categories

Track exactly which layer drifted:
	•	wallet_drift
	•	position_drift
	•	settlement_drift
	•	order_drift
	•	mark_price_stale
	•	rpc_stale
	•	backend_sequence_gap

Reconciliation behavior

If drift < tiny threshold

Mark green.

If drift moderate but explainable

Mark yellow and set reason reconciling.

If drift large

Emit RECONCILIATION_WARNING, log aggressively, optionally show warning badge.

If correction succeeds

Emit RECONCILIATION_CORRECTED.

16. Handling stale data

Every subsystem should report freshness.

Example thresholds
	•	mark price stale after 3s
	•	Typus state stale after 8s
	•	wallet state stale after 15s
	•	reconciliation stale after 30s

If stale:
	•	color should degrade away from green
	•	reason should become stale
	•	UI should optionally show a small freshness timer

Green should never be shown for stale state.

23. Failure handling

If Typus endpoint fails
	•	keep last known position state
	•	mark confidence blue or yellow, not green
	•	set stale flag
	•	retry on backoff

If wallet RPC fails
	•	retain prior confirmed wallet
	•	mark stale
	•	do not zero out balances

If websocket disconnects
	•	UI falls back to snapshot polling
	•	on reconnect, refetch snapshots

If reducer receives conflicting data
	•	prefer authoritative reconciliation event
	•	log inconsistency
	•	emit correction event

24. Example lifecycle

Open position flow
	1.	Agent submits order
	2.	Event: ORDER_SUBMITTED
	3.	UI shows yellow “opening”
	4.	Tx confirms
	5.	Event: ORDER_ACCEPTED
	6.	Typus shows active order / fill
	7.	Event: ORDER_FILLED
	8.	Event: POSITION_OPENED
	9.	UI shifts blue “estimated”
	10.	Reconciliation validates all components
	11.	UI shifts green if no unresolved transition remains

Close position flow
	1.	Close requested
	2.	Event: POSITION_CLOSE_REQUESTED
	3.	UI yellow “closing”
	4.	Typus no longer shows open position
	5.	Event: POSITION_CLOSED
	6.	Position moved to settling bucket
	7.	pendingSettlementAmount increases
	8.	UI yellow “settling”
	9.	Wallet receives funds
	10.	Event: SETTLEMENT_CONFIRMED
	11.	Reconciliation validates
	12.	UI green “verified”

This is the exact behavior users need to see.
