Implement the operational Blue Water Agents trading system. Do not produce another architecture-only update, static mockup, or list of blockers. Inspect the existing repository first, preserve unrelated working behavior and historical data, then implement and test the requirements below.

The product is a public, multi-user Sui application. Remove all owner-console and OWNER_CONTROL_TOKEN concepts. Any visitor must be able to connect a Sui wallet, authenticate by signing a human-readable nonce, create their own isolated agent wallet, choose Paper or Mainnet mode, fund the agent, monitor it, pause it, and withdraw assets back to the authenticated owner wallet.

Do not claim profitability or imply that 10 SUI will become 100 SUI. “10 → 100 SUI” may remain an experimental campaign target, but the UI must clearly distinguish target, current liquidation value, realized P&L, unrealized P&L, fees, gas, and returned SUI.

1. Replace the false status UI

Remove every hard-coded operational status from the frontend.

Every status must come from a backend health contract containing:

* status: HEALTHY, DEGRADED, BLOCKED, or UNKNOWN
* checkedAt
* lastSuccessAt
* lastCheckpoint
* lagSeconds
* evidenceCount
* reason
* version

Do not report a collector as healthy merely because an HTTP provider responded. Healthy must mean:

* the process lease is current;
* the checkpoint is advancing;
* events are being persisted;
* replay is functional;
* the newest verified event is within the permitted lag;
* the Sui provider and Suipump discovery source agree within configured tolerances.

All action handlers must check response.ok, parse structured errors, show the error to the user, and never make a failed action look successful.

3. Implement a durable Mainnet collector

Run the production deployment as an always-on Replit Reserved VM, not Autoscale.

Implement a persistent collector with:

* checkpoint cursor stored in PostgreSQL;
* backfill from the last committed checkpoint;
* live polling or streaming after backfill;
* raw event storage before normalization;
* transaction digest and event sequence as an idempotency key;
* retry with bounded exponential backoff;
* dead-letter records for malformed events;
* reorg/finality-safe processing where applicable;
* duplicate-free restart and replay;
* data-source reconciliation between Suipump discovery data and Sui on-chain events.

Collect launches, buys, sells, graduations, curve state, reserves, fees, creators, holders, token types, shared versions, checkpoints, timestamps, transaction digests, and package lineage.

Backfill historical data immediately where the provider and chain permit. Do not use “wait fourteen days” as a product blocker.

5. Implement genuine forward-only Paper trading

Each authenticated user can create a Paper campaign starting with 10 virtual SUI.

Paper mode must use the same:

* candidate universe;
* ranking engine;
* strategy;
* risk policy;
* protocol manifest;
* transaction builder;
* quote engine;
* fee model;
* gas estimator

as Mainnet mode. The only difference is that Paper mode does not sign or submit the transaction.

For every paper decision:

1. Freeze the decision timestamp and Sui checkpoint.
2. Store the complete candidate/ranking snapshot.
3. Build the exact intended transaction.
4. Obtain a fresh quote.
5. Run Sui transaction simulation whenever the required inputs can be represented faithfully.
6. Store simulation effects, balance changes, gas estimate, errors, and a hash of the simulated transaction.
7. If faithful simulation is impossible, mark the order UNEXECUTABLE; never invent a fill.
8. Apply protocol fees, price impact, slippage, and estimated gas to the virtual ledger.
9. Open or close a virtual position using only information available at that time.
10. Revalue positions using fresh executable exit quotes—not displayed last-trade prices.

Paper activity must show:

* decision ID
* candidate score and components
* entry or exit reason
* quote input/output
* expected and simulated gas
* slippage and fees
* checkpoint
* simulation status
* virtual fill
* resulting position
* realized and unrealized P&L
* evidence links

No random returns, synthetic transaction digests, hindsight pricing, or backdated decisions.

7. Implement deterministic Mainnet execution

The execution state machine must be:

CANDIDATE → DECISION → QUOTED → SIMULATED → APPROVED_BY_POLICY → SIGNED → SUBMITTED → FINALIZED → RECONCILED

Implement idempotency at every transition. A retry must never submit the same economic order twice.

Before every submission:

* confirm the agent remains armed and funded;
* refresh the protocol manifest;
* refresh the curve object and shared version;
* refresh the quote;
* reject stale quotes;
* require a strictly positive minimum output;
* enforce slippage and price-impact limits;
* simulate the completed transaction;
* compare simulation with the decision;
* verify sufficient SUI remains for gas and withdrawal;
* record the serialized transaction hash.

After submission:

* wait for finality;
* store the real transaction digest;
* parse effects and balance changes;
* reconcile expected versus actual token and SUI changes;
* update the double-entry ledger;
* link the explorer URL;
* pause that agent automatically on any unexplained discrepancy.

Use the current @mysten/sui v2 client and current dApp Kit packages. Do not introduce new deprecated JSON-RPC-only code.

8. Mainnet canary

Mainnet must require a separate, human-readable “Arm Mainnet” signature from the owner. Funding an address alone must not arm trading.

Implement an initial round-trip canary:

* owner-configured amount with 0.01 SUI default;
* hard maximum 0.1 SUI;
* highest-liquidity candidate that passes every hard filter;
* verified buy route;
* finality and balance reconciliation;
* verified sell route;
* finality and reconciliation;
* return to SUI;
* complete activity evidence.

Do not execute the canary until the user funds and explicitly arms that specific agent. Do not fabricate a digest if it has not happened.

After the canary, leave general live strategy disabled until the round-trip reconciliation test passes.

Default live safeguards:

* maximum two open positions;
* no leverage or borrowing;
* never average down;
* reserve at least 1 SUI or 20% of assets for gas/withdrawal, whichever is greater;
* maximum initial order 0.1 SUI;
* maximum slippage 3%;
* maximum entry price impact 2%;
* maximum exit price impact 5%;
* quote age maximum 5 seconds;
* daily loss limit 5%;
* circuit breaker after three consecutive execution or reconciliation failures.

Make thresholds configurable per user only within server-enforced safe bounds.

9. Withdraw and emergency controls

Pause must immediately prevent new entries while preserving exits and withdrawals.

“Withdraw All” must:

1. stop new entries;
2. cancel pending orders where possible;
3. sell positions only through verified routes and within configured exit limits;
4. return liquid SUI to the authenticated owner;
5. return unsellable residual tokens to the owner rather than trapping them;
6. preserve the gas required to finish;
7. record every transaction and refusal reason.

A user must never need an admin or OWNER_CONTROL_TOKEN to recover their assets.
