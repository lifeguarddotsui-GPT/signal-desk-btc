3. Development changes

  • Settlement: Independent startup/timer reconciliation replaces live-poll-triggered settlement work. Existing database due rows and atomic, expiring per-round claims provide restart recovery and idempotency. Incomplete proofs still reach the strict validator and retain withheld reasons; exact-round mismatches fail closed.
  • Limit: This queue covers existing learning rows, not orphaned saved decisions whose learning metadata was never persisted. That remaining scope needs independently established settlement evidence and provenance-safe recovery.
  • Scheduling: A five-second independent runtime tick retries still-valid frozen candidates and records expiry failures without waiting for a new provider tick. Bounded restart recovery records missing durable assessments, never invented historical evaluations or locks.
  • Confirmation: Qualified interval/stage policy remains mandatory. Unavailable policy is a legitimate abstention; deadlines and thresholds were not relaxed to force Confirmation locks.
  • Identity/scoring: Shared WaterX BTC mainnet identity covers interval, provider round ID, start and expiry. Restore/history guards also enforce market, network, stage and strategy. Each lock scores independently against strict, exact-round verified settlement.
  • History: Verified/pending/withheld/disputed/missing/mismatch settlement states, independent stage scores, both choices and timestamps, lead time, timing basis, abstention/data-failure counts, agreement/disagreement and paired-cohort rates. No paired data displays as unavailable. Indicative entry economics remain labelled research estimates, never executable quotes, fills or P&L.

4. Actual provider payloads and proof semantics

Current adapters parsed actual ended 5m and 15m responses. Provider settledAt was respectively 53 and 54 seconds after expiry. The supplied historical epoch selects the closing boundary. There is no evidence requiring weaker post-expiry timestamp checks.

The provider nested settlement.finalPrice was 1 while the BTC/USD round settlePrice was approximately 81,000. Those fields cannot be treated as the same unit. Outcomes in these payloads were DOWN and consistent with confirmed anchors and closing prices. This is provider consistency, not independent Chainlink/on-chain verification. No new historical production backfill was authorized or performed.

Development startup also exposed a historical response rejected by the existing 1MB body limit, and an adaptive-research reproducibility warning. Those failures remain visible and fail closed; running UI and passing tests do not establish that every historical provider response is recoverable.

6. Rollout and rollback plan

  1. Before production collector or schema rollout, satisfy the existing gate: current complete export, successful isolated restore, private off-workspace retention and approved hosting/cost constraints. This audit did not establish that gate.
  2. Review the managed publication/schema diff. These repairs add no schema migration; do not accept unrelated pending schema changes implicitly. Keep mainnet release, signer and automatic execution disabled.
  3. Publish only after owner approval. Record the new runtime version, retain this old-build manifest, and compare fixed-cutoff production cohorts, pending/orphan counts, missed assessments, retry failures and identical historical decision fingerprints.
  4. If regressions occur, use the pre-repair checkpoint corresponding to the known October 8 deployed source and republish through the normal owner-controlled flow. Verify the runtime commit/build again; do not roll back to older GitHub main as if it were current production.
  5. Do not delete prediction tables, rewrite old locks, manufacture missing choices or drop audit records as rollback. No database rollback is needed for these development changes alone; any later separately approved migration requires its own restore plan.
