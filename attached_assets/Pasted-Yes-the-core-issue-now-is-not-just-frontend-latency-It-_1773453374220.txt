The real problem

Right now the app is likely asking:

	•	what is in current positions?

For every SUI ever deposited, what is its current economic state?

Until the architecture can answer that deterministically, Total Economic Value and PnL will keep looking fake and frightening.

The principle to enforce

You need a hard invariant:

SUI Accountability Invariant

For a given user:

Net Deposited = Wallet Balance + Open Position Margin/Equity + Pending Transfers/In Transit + Claimable Rewards + Settled Realized Losses + Withdrawn Value + Fees

Or rearranged into something UI-friendly:

Total Economic Value = Wallets + Positions + In Transit + Rewards

and

Unaccounted Value = Net Deposited - (Wallets + Positions + In Transit + Rewards + Withdrawals + Known Fees + Realized Losses)

Critical rule

Unaccounted Value should never silently disappear.

If the system cannot prove where value is, it must explicitly show:
	•	Unattributed / Investigating
	•	or Pending Reconciliation

Never just let it vanish into a lower PnL.

The most important missing concept

Transitional value must be first-class

Your screenshots prove this is where the system still breaks.

When a position closes or money is being moved, the value is often in one of these phases:
	•	exchange says position closed
	•	margin not yet reflected in wallet
	•	settlement triggered but not verified
	•	backend knows action happened but destination not confirmed
	•	reward is claimable but not yet claimed
	•	reward claim submitted but not yet arrived

Those are not edge cases.
Those are normal portfolio states.

So “In Transit” cannot be cosmetic. It must be backed by real data.

⸻

What “In Transit” should actually mean

In Transit should be the sum of:
	•	closing position collateral pending release
	•	unrealized/realized proceeds waiting settlement
	•	transfer from agent wallet to user wallet pending confirmation
	•	reward claim pending receipt
	•	withdrawals initiated but not yet landed
	•	any protocol state where source is debited but destination not yet verified

Formula

inTransitValue =
  positionClosingValue +
  settlementPendingValue +
  transferPendingValue +
  rewardClaimPendingValue +
  withdrawPendingValue

And the UI should let you drill into it.

Example:
	•	3.20 SUI closing settlement
	•	1.10 SUI reward claim pending
	•	0.85 SUI wallet transfer pending

Total In Transit: 5.15 SUI

That is how you prevent panic.

That is the exact bug class.

Position lifecycle plan

You already liked tracking orders and positions separately. This should go further.

Position state machine

type PositionLifecycle =
  | 'OPENING'
  | 'OPEN'
  | 'REDUCING'
  | 'CLOSING'
  | 'CLOSED_UNSETTLED'
  | 'SETTLING'
  | 'SETTLED'
  | 'FAILED'

Rules
	•	OPEN: counted under Positions
	•	CLOSING: still counted under Positions or split between Positions/In Transit depending on platform semantics
	•	CLOSED_UNSETTLED: no longer open, but value must move to In Transit
	•	SETTLING: fully in In Transit
	•	SETTLED: moved into Wallets

Do not let closed positions disappear before value lands.

Reconciliation algorithm

On every cycle:

Step 1 — load known constants
	•	net deposits
	•	withdrawals
	•	lifetime fees if available

Step 2 — load live state
	•	user wallet balances
	•	agent wallet balances
	•	open positions
	•	mark prices
	•	claimable rewards
	•	pending transfers
	•	pending settlements

Step 3 — map each value source into buckets

Step 4 — calculate attributed total

attributed =
  wallets +
  positions +
  inTransit +
  rewards +
  withdrawn +
  knownRealizedLosses +
  fees

Step 5 — calculate unattributed

unattributed = netDeposited - attributed

Step 6 — classify status
	•	if unattributed near zero: verified
	•	if small and temporary: syncing
	•	if meaningful and old: reconciliation warning

Step 7 — publish snapshot
