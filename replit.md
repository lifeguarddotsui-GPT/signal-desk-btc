# Blue Water Agents - AI Trading Platform

## Overview
Blue Water Agents is a Web3 AI trading platform for autonomous trading of SUI-USDC perpetual contracts using a dual-agent architecture. It offers a Market Dashboard with live Pyth Oracle data, charting, and AI Signal Reasoning. The platform focuses on transparency and user control, enabling deployment, management, and monitoring of AI trading agents with auditable on-chain transactions. The project's vision is to provide a robust, transparent, and user-centric platform for AI-driven perpetual futures trading within the Web3 ecosystem.

## System Architecture
The platform utilizes a React, Vite, Tailwind CSS, and shadcn/ui frontend, integrated with SUI wallets. The backend is built with Express.js, PostgreSQL (managed by Drizzle ORM), and incorporates a WebSocket server for real-time data communication.

**Core Architectural Decisions & Features:**

*   **Dual-Agent System:** Each deployment includes an Execution Agent (managing wallet, orders, positions, and risk) and a Signal Sub-Agent (performing indicator analysis and generating trading signals). **Triton Signal Engine** (`server/signal-engine.ts`): Regime-aware, multi-timeframe signal engine with **Aggressive/Precision/Auto mode toggle** per agent (`agents.signalMode` column). Uses weighted scoring across ADX, HTF alignment, EMA distance, RSI, volume, MACD turn, liquidity sweeps, and R:R. Mode profiles define thresholds: AGGRESSIVE (minScore 40/55, wide EMA dist ≤2.5%, RSI 22-82, vol ≥0.45x, momentum continuation + trend momentum entries allowed, RR gates 0.7/0.5) vs PRECISION (minScore 62/72, tighter filters, MACD turn required for weak trades, RR gates 1.5/1.2). AUTO mode selects dynamically based on ADX/ATR/volume conditions (favors AGGRESSIVE when vol ≥1.0x or ADX ≥22). Dashboard shows `activeMode` badge. Agent config UI has 3-way mode toggle (wallet-authenticated via query param). Per-agent signal generation computes fresh signal with agent's configured mode. Execution engine enforces double gating (signal engine + execution engine both check score/RR vs mode profile). **Loss Cooldowns**: 3-minute cooldown after loss, 30-minute cooldown after 3 consecutive losses. **Multi-TF Candles**: 5m/1h/4h candle data maintained in `server/market-engine.ts`, exposed via `GET /api/market/candles/multi`.
*   **DEX Execution Engine:** Uses a `DexAdapter` interface for Typus Perps, executing direct on-chain Move calls. Includes keeper-based market orders, per-position close gas caps, and strict market order enforcement with slippage. **Market Close Builder:** Close orders use zero collateral (reduce-only), correct close direction (`closeIsLong = !positionIsLong`), `isStopOrder=false`, and dedicated `marketCloseTriggerPrice()` with `CLOSE_SLIPPAGE_BPS=500` (5%) for immediate fills. Closing a LONG sets trigger BELOW market (sell); closing a SHORT sets trigger ABOVE market (buy).
*   **Position Lifecycle State Machine:** Strict `pending_open` → `open` → `closed` lifecycle. Positions are created as `pending_open` and only promoted to `open` when `onChainPositionId` is confirmed via TX digest parsing (objectChanges + events), order ID resolution, wallet TX history, or heuristic on-chain matching. Close button disabled for `pending_open` positions; UI shows "Opening... verifying on-chain" with amber indicator. Positions stuck in `pending_open` for >10m auto-escalate to `error` status. **Deterministic Reconciliation:** `reconcileFromDigest()` parses both `objectChanges` (created Position objects) and protocol events (CreateTradingOrderEvent, OrderFilledEvent, FillTradingOrderEvent) from the open TX digest. **Multi-Level Close Recovery:** Close flow never hard-rejects — runs Level 0 (digest reconciliation) → Level 1 (stored orderId) → Level 2 (wallet TX history) → Level 3 (heuristic on-chain match / balance-confirmed settlement). **Background Verify & Recover:** 30s background loop scans all agents for `pending_open` or ID-less `open` positions, attempting digest reconciliation → order resolution → on-chain matching. Digest reconciliation loop runs every 15s for in-flight positions. **PnL Integrity:** Robust handling of Typus's two-step `position_id` assignment with `typusOrderId` stored at open time for reliable close resolution. Open flow re-fetches TX receipt via `waitForTransaction` + `getTransactionBlock` for deterministic event capture. All force-settle paths require on-chain balance confirmation before marking positions closed. Features close fill verification, collateral protection, price guard protection, and on-chain liquidation detection with PnL recalculation and startup integrity checks.
*   **Idempotent Close State Machine:** DB-persisted close state tracking per position (`closeState`, `closeAttempts`, `lastCloseTx`, `closePendingSince`). States: `open` → `close_requested` → `close_tx_submitted` → `close_order_working` → `closed` / `manual_review`. Prevents close spam by refusing to resubmit while a close is pending on Typus (45s watchdog TTL). Hard stop after 5 total close attempts (persisted, not resettable by recovery). Minimum 15s gap between close retries. Blocked recovery respects DB attempt limits and won't reset gas tracking indefinitely. **Close Confirmation Loop:** After close TX success, waits 2s then queries on-chain `getPositions` to verify position is actually gone — if still visible, reverts to `close_order_working` for auto-retry. **Dry-Run Preflight:** Before executing real close TX, runs `dryRunTransactionBlock` to catch Move abort errors without burning gas. **Tracked-Order Fill Detection:** DB scan checks `typus_tracked_orders` for close orders — if all submitted and position gone on-chain, confirms keeper fill.
*   **Transaction Safety & Recovery:** Implements a per-wallet transaction queue, `CoinManager` for gas reserves, `safe-execute` with retry logic, and dry-run preflights. Includes orphaned order recovery and pre-close cleanup mechanisms. **Three-Layer Order Cleanup:** Pre-close runs `cancelAllLinkedOrdersViaWalletHistory` (fast wallet TX scan), `too_many_linked_orders` error escalates to `deepCancelLinkedOrders` (global event scan, 20 pages), then unlinked close (no `linked_position_id`) as last resort. Final `checkPriorCloseFilled` recheck catches keeper fills during retry window.
*   **Anti-Liquidation Protection:** A three-tier system (stop-loss auto-tightening, max collateral loss cap, emergency close) protects against liquidation. Features per-position close gas caps, pre-close existence checks, unresolved position guards, and strict RPC balance policies. Daily gas caps auto-pause agents.
*   **Monitoring and Control:** A `Position Monitor` continuously checks open positions. A `Circuit Breaker` pauses agents after consecutive failed operations, and a `Daily Spend Cap` pauses agents if gas costs exceed thresholds. Includes mechanisms for handling "phantom linked orders" and persistent gas cap tracking.
*   **Oracle Integration:** Primary price data is sourced from Pyth Network's Hermes API (SUI/USD), with price validation and stale price guards.
*   **Gas Management:** Employs a two-tier gas policy and dynamic budgeting with a safety margin. Supports coin merging.
*   **Agent Ownership & Rewards:** Agents are tied to the creator's wallet, with configurable rewards escrowed on-chain upon profitable position closure. Includes force-settle recovery mechanisms using hybrid event query and wallet TX history approaches.
*   **Comprehensive Portfolio Display:** The "My Agents" page provides on-chain-verified breakdown of Total Portfolio Value, On-Chain Wallet balance, In Positions, In Pending Orders, Unrealized PnL, and an Accounting section. Includes unrecovered SUI detail display. **Balance Audit** (`GET /api/agents/audit`): Cross-references all agent DB balances against on-chain SUI balances and auto-syncs discrepancies >0.01 SUI. **External Wallet Registration** (`POST /api/agents/register-wallet`): Registers pre-existing wallets as tracked agents with on-chain balance sync. Startup auto-registers known wallets (Triton 3, Triton 4) via `ensureExternalWalletsRegistered()`.
*   **SUI Flow Tracker:** A dedicated page and API endpoint (`/api/agents/:id/sui-flow`) scans on-chain wallet transaction history, categorizes SUI movements, and identifies likely liquidations with detailed explanations.
*   **TX Inspector:** `GET /api/tx/:digest/inspect` endpoint returns detailed balance changes, created coins, events, gas costs, and sender for any Sui transaction digest — used to diagnose where returned SUI goes after close TXs. Post-close flow automatically inspects close TX balance changes via `inspectCloseTxBalanceChanges()` and logs warnings if SUI went to wrong address.
*   **Learning Engine** (`server/learning-engine.ts`): Tracks close outcomes in `close_outcomes` table and maintains `policy_weights` using EWMA-based reward scoring. Every position close logs method, regime, latency, slippage, PnL. `computeReward()` assigns scores (+2.5 success, -2.5 fail, speed/slip bonuses). `updateWeights()` updates per-regime per-action weights with EWMA (alpha=0.15). `getPreferredCloseMethod()` uses UCB (Upper Confidence Bound) bandit algorithm for action selection. Stats exposed via `GET /api/learning/stats`.
*   **UI/UX Design:** Features a dark crypto trading theme with a teal primary color, CSS variable-based charting, and mobile-first responsive design.
