You’re not seeing “fake” liquidations from a Typus Keeper comms bug — you’re seeing real on-chain liquidations that are happening because the position stays open (or is opened with liq distance too tight), while your app/bot fails to close in time.

From your screenshots:
	•	Triton 3 shows a real LIQ of 6.6093 SUI → 0.0000 at 10:57 AM. That’s a full collateral wipe.
	•	Your Errors tab shows repeated Failed Close (-0.0009 SUI) transactions (gas burn) — meaning the bot is trying to close, paying gas, but the close TX is failing, so the position remains open and can get liquidated.
	•	Triton 4 has two liquidations that occur the same minute as the order create (10:55 and 11:00). That strongly indicates leverage/maintenance margin makes liquidation closer than your intended SL, OR the bot didn’t actually attach working SL/TP / didn’t close, so liquidation hit first.

The real “root cause” is almost always one (or a combination) of these:
	1.	Close calls are constructed with the wrong on-chain object(s) (wrong positionId, wrong accountCap, wrong market/clearing object, stale object version, etc.) → TX fails → position never closes → liquidation.
	2.	Your system is marking closes as “done” without checking on-chain effects, so the UI thinks it closed, but it didn’t.
	3.	Your SL is tighter than liquidation distance at 25–36x, so liquidation can occur before your SL logic can execute (especially if maint margin is high or price/oracle is jumpy).
	4.	You are misclassifying transactions in the UI (ex: showing Order Create -0.0102 SUI for order 994 while it clearly corresponds to a large settlement/close). That’s a parsing/indexing bug that hides what really happened.

3) Fix Close: one close call, correct objects, confirmed state change

Those repeated Failed Close -0.0009 SUI are your bot burning gas without ever closing.

Add a strict close state machine

requestClose(positionObjectId, reason)
	1.	Load position record
	2.	If status in (CLOSED, LIQUIDATED) → return (idempotent)
	3.	Set status=PENDING_CLOSE, increment closeAttempts
	4.	Build close TX using positionObjectId (not local order id)
	5.	Submit TX
	6.	Wait for confirmation
	7.	On success:
	•	Verify position is now closed on-chain (see step 4 below)
	•	Set status=CLOSED, store closeTxDigest, store returned amount
	8.	On failure:
	•	Parse and classify error (below)
	•	Set status=FAILED_CLOSE
	•	Stop retry spam (cooldown + max attempts)

Add error classification (so you know why it fails)

Parse effects.status.error (and any Move abort code) into buckets:
	•	ERR_POSITION_NOT_FOUND → your positionObjectId is wrong or never existed
	•	ERR_OBJECT_VERSION / ERR_SHARED_OBJECT_VERSION → stale ref, must refetch objects
	•	ERR_NOT_AUTHORIZED → wrong signer / missing capability (account cap not owned by agent)
	•	ERR_INSUFFICIENT_GAS → gas coin mgmt broken
	•	ERR_SLIPPAGE / ERR_PRICE_TOO_FAR → you used a close that needs tolerance, fix params
	•	ERR_ALREADY_CLOSED → treat as success, mark closed

Log the bucket + raw error.

Add backoff & cap
	•	Max close attempts per position: 3
	•	Retry delay: 15s, then 60s, then stop + alert UI

This alone will stop burning SUI.
