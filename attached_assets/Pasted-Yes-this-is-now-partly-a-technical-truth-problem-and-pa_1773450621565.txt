Yes — this is now partly a technical truth problem and partly a product psychology problem.

Even if the backend becomes much better, users will still panic if the first thing they see is:
	•	Net Deposited: 39.20
	•	Portfolio: 18.88
	•	yellow / blue / adjusting / checking

That visually reads as:

“I deposited 39.2 and now I only have 18.88.”

Even if the missing value is actually in:
	•	open positions
	•	closing positions
	•	unsettled margin return
	•	pending keeper settlement
	•	reserved order collateral
	•	stale frontend state

So the plan needs two major upgrades:

1. Stop showing a single ambiguous portfolio number without composition

Right now the UI compresses too much into one scary number.

Instead, every agent and the top portfolio card should always decompose value into persistent buckets.

New primary value model

For both user and agent, always show:

Total Economic Value =
Wallet Balance
+ Open Position Value
+ Pending Settlement
+ Reserved Orders

Not just “portfolio” as one number.

Better top card layout

Instead of:
	•	Net Deposited
	•	Total PnL
	•	Rewards
	•	one large portfolio number

Use:

Under it, a compact breakdown:
	•	Wallets: 14.2

Then separately:
	•	Net Deposited: 39.2
	•	Realized PnL: -3.1
	•	Unrealized PnL: +1.6

That way users can understand where the value is.

Because the real fear is not “my value is blue.”
The fear is:

“Where did the rest of my money go?”

So the UI must answer that directly.

2. Pin every position through its full lifecycle

This is the most important frontend rule.

A position must never disappear simply because one endpoint stopped reporting it before the next subsystem caught up.

Golden rule

Once a position is seen by the system, it remains visible until it reaches a terminal lifecycle state and the financial consequences are accounted for.

That means a position must persist through:
	•	opening
	•	open
	•	reducing
	•	closing
	•	closed awaiting settlement
	•	settled
	•	archived

Position lifecycle states

Use these states explicitly:

type PositionLifecycle =
  | 'detected_opening'
  | 'opening'
  | 'open'
  | 'reducing'
  | 'closing'
  | 'closed_pending_settlement'
  | 'settled'
  | 'archived'
  | 'error';

UI persistence rule

Once a position enters any non-terminal state, keep it pinned in UI until:
	•	settlement amount is confirmed
	•	wallet delta is observed or reconciled
	•	final realized pnl is known
	•	state moves to settled

Only then move it to history/archive.

So even if Typus momentarily stops showing the position, your UI still shows:

BTC Long — closing — settlement pending — est return 4.23 SUI

That is vastly better than:
	•	“0 positions open”
	•	wallet balance looks low
	•	user assumes funds vanished

Add a dedicated bucket

Capital In Transit

This includes:
	•	closing positions not fully settled

7. Build a “position registry” so frontend never loses track

You need a backend object that outlives raw live endpoint visibility.

New concept: Position Registry

A durable store keyed by:
	•	agentId
	•	market
	•	positionId if available
	•	fallback deterministic hash if Typus identifiers are weak

The registry stores:
	•	first detected time
	•	last confirmed time
	•	current lifecycle state
	•	source confidence
	•	expected settlement
	•	final realized pnl
	•	archival time

Registry rule

A position is not removed when a source no longer reports it.
It is removed only when:
	•	lifecycle reaches terminal state
	•	reconciliation confirms settlement complete
	•	archival timeout passes

This fixes “backend knew it, frontend lost it.”

8. Use hysteresis to prevent flicker and disappearing states

Another issue is UI flicker: position visible, then gone, then visible.

Apply hysteresis

If a position was visible in the last N seconds and no terminal close has been confirmed, keep it shown.

Suggested rules:
	•	open position disappearance requires 2–3 consecutive missed syncs before downgrading confidence
	•	but even then it moves to closing/checking, not disappears
	•	only after close+settlement+reconcile does it leave active view

This is much more humane.

9. Add “shadow state” for recently lost visibility

When a source goes silent, do not erase the item.

Move it to a shadow state:

type VisibilityState =
  | 'live'
  | 'shadow'
  | 'reconciling'
  | 'terminal';

Example

If Typus stops reporting an open position unexpectedly:
	•	keep position in UI
	•	mark it reconciling
	•	show last known size/entry
	•	set color yellow
	•	do not remove economic value immediately

This prevents phantom losses.

14. Backend implementation changes to support pinned lifecycle

Tell the backend to create three separate persistent collections:

A. orders

For open/partial/cancel/fill lifecycle.

B. positions

For live and closing positions.

C. settlements

For closed-but-not-landed capital.

This is cleaner than trying to force one object to represent everything.

Suggested settlement object

interface PendingSettlement {
  settlementId: string;
  agentId: string;
  positionId: string;
  market: string;
  expectedReturn: number;
  expectedMarginReturn: number;
  expectedRealizedPnl: number;
  status: 'pending' | 'observed' | 'reconciled' | 'failed';
  createdAt: number;
  updatedAt: number;
}

Then frontend can render “In Transit” directly from this.

20. My strongest product recommendation

The biggest UX fix is this:

Change the main displayed number from “portfolio balance” to “total economic value,” and always break it into wallets + live positions + in-transit capital.

That alone will reduce the feeling of phantom losses massively.

The biggest technical fix is this:

Implement a durable position registry plus settlement registry so positions remain pinned through open, close, and settlement instead of disappearing when one data source lags.

Those two together solve both the truth problem and the psychological trust problem.
