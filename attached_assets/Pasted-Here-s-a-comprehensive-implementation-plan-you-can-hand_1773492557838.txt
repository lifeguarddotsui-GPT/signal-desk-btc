Here’s a comprehensive implementation plan you can hand to the Replit agent.

Goal

Make the User Wallet / My Portfolio card reflect the true economic value of the user across:
	•	connected wallet balances
	•	agent active margin / open positions
	•	agent saving wallets
	•	unsettled PnL
	•	rewards
	•	transfers in flight
	•	pending settlements / closeouts

The system should stop relying on a few fragile frontend RPC reads and instead move to a ledger + state-machine + reconciliation model.

⸻

Core diagnosis

Right now the UI problems are coming from 4 structural gaps:

1. Agent Saving Wallet balances are not part of portfolio aggregation

The portfolio card is likely summing only:
	•	user wallet settled balance
	•	maybe reward wallet
	•	maybe some agent wallet balances

But it is not including every custody location where user-owned SUI can live.

That means the app is under-reporting true value.

⸻

2. Too much “unaccounted” SUI

This usually means the app does not maintain a full internal accounting model of:
	•	deposits to agents
	•	transfers between protocol wallets
	•	collateral locked in positions
	•	realized but unsettled flows
	•	pending close / settle txns
	•	reward accrual paths
	•	agent saving wallet balances

Without a canonical ledger, the UI is trying to infer reality from snapshots, and snapshots miss lifecycle state.

⸻

3. In Transit is null

This means there is no durable transfer-tracking pipeline.

The frontend probably asks:
	•	“what is current wallet balance?”
	•	“what is current agent balance?”

But it does not track:
	•	transfer initiated
	•	tx submitted
	•	tx confirmed
	•	funds received
	•	funds indexed
	•	funds reconciled

So anything between source and destination becomes invisible.

⸻

4. Positions often null / incomplete

This means open positions are being fetched too narrowly or too late, probably with:
	•	weak polling
	•	no backend cache
	•	no lifecycle persistence
	•	position state lost during open/close transitions
	•	reliance on only one API source

The result: position value disappears temporarily and portfolio looks broken.

⸻

What to build instead

Build a Portfolio Accounting Engine with 4 layers:

Layer 1 — Canonical Ownership Registry

Create a registry of all wallets / subaccounts / custody buckets belonging to the user.

For each user, maintain:
	•	primary_wallet
	•	reward_wallet
	•	agent_wallets[]
	•	agent_saving_wallets[]
	•	protocol_temp_wallets[] if applicable
	•	exchange_subaccounts[] if Typus/keeper style accounts exist
	•	position_margin_accounts[] if separate from wallet

Each entry should include:
	•	wallet address
	•	wallet type
	•	owner user id
	•	agent id if applicable
	•	chain/network
	•	active/inactive
	•	discovery source
	•	last verified balance
	•	last verified block/txn checkpoint

Required fix

The portfolio aggregator must sum all user-owned balance locations, including:
	•	primary wallet
	•	agent operational wallet
	•	agent saving wallet
	•	claimable rewards
	•	margin currently sitting idle in trading subaccounts

If the money belongs economically to the user, it must show up somewhere.

Reconciliation Engine

Create a backend worker that runs every few seconds and performs 3 independent reconciliation passes.

Pass A — Wallet Balance Reconciliation

For every registered wallet:
	•	fetch on-chain balance
	•	fetch recent txns since last checkpoint
	•	update wallet snapshot
	•	classify inflows/outflows into ledger events if matched
	•	flag unmatched balance deltas

Pass B — Position Reconciliation

For every agent:
	•	fetch open positions from Typus / exchange source
	•	fetch recent fills / order updates / margin updates
	•	update position_registry
	•	compute locked margin + unrealized pnl
	•	detect closed-but-unsettled positions

Pass C — Economic Value Reconciliation

Compute:

economic_value = settled_wallets + saving_wallets + rewards + margin_idle + margin_locked + unrealized_pnl + in_transit + pending_settlement

Then compare against:
net_deposited + realized_pnl - withdrawals - fees - losses

Any unexplained difference becomes:
	•	reconciliation_gap

The goal is to shrink this gap close to zero.

New portfolio accounting model

Instead of the current simplistic card, use these buckets:

Settled Wallets

Confirmed balances currently sitting in:
	•	user wallet
	•	agent operational wallet
	•	agent saving wallet
	•	reward wallet
	•	protocol wallets owned by user

Active Positions

Sum of:
	•	locked margin
	•	unrealized pnl

Formula:
positions_value = locked_margin + unrealized_pnl

Not just “market live.”
This should represent actual economic exposure.

In Transit

Transfers not yet fully reconciled.

Formula:
sum of tracked transfer jobs with pending statuses.

Pending Settlement

Funds from recently closed positions, keeper settlement, closeout paths, claim paths, etc. that are expected but not yet landed in settled wallets.

Rewards

Claimable rewards not already included elsewhere.

Reconciliation Gap

Only show this if necessary:
gap = expected_total - observed_total

This is a diagnostic bucket, not a permanent crutch.

3. Make In Transit real

What backend must do

Whenever app initiates a transfer:
	•	create transfer job immediately
	•	save expected amount and route
	•	watch tx hash
	•	poll destination wallet for receipt
	•	mark reconciled only when destination balance delta or matching receive event is detected

Pseudocode

async function createTransferJob(input) {
  return db.transferJobs.insert({
    userId: input.userId,
    agentId: input.agentId,
    asset: 'SUI',
    amountExpected: input.amount,
    fromAddress: input.from,
    toAddress: input.to,
    transferType: input.transferType,
    status: 'CREATED',
    initiatedAt: new Date(),
  });
}

async function onTransferSubmitted(jobId, txHash) {
  await db.transferJobs.update(jobId, {
    initiationTxHash: txHash,
    status: 'SUBMITTED',
    submittedAt: new Date(),
  });
}

async function reconcileTransfer(job) {
  const tx = await chain.getTransaction(job.initiationTxHash);

  if (tx.confirmed && job.status === 'SUBMITTED') {
    await updateJob(job.id, {
      status: 'ONCHAIN_CONFIRMED',
      confirmedAt: new Date(),
    });
  }

  const destinationObserved = await detectDestinationReceipt(job.toAddress, job.amountExpected);

  if (destinationObserved) {
    await updateJob(job.id, {
      status: 'DESTINATION_OBSERVED',
      receiveTxHash: destinationObserved.txHash,
      receivedAt: new Date(),
    });
  }

  if (tx.confirmed && destinationObserved) {
    await updateJob(job.id, {
      status: 'RECONCILED',
      reconciledAt: new Date(),
    });
  }
}

UI behavior

If sum is zero, show:
	•	0.00 SUI
	•	subtitle: no transfers pending

Never null.

4. Make Positions reliable

Main fix

Maintain positions on backend independent of frontend polling.

The frontend should never be responsible for discovering live positions from scratch.

Backend polling sources

Use multiple sources if available:
	•	exchange/Typus positions endpoint
	•	recent fills/orders endpoint
	•	local submitted order registry
	•	chain settlement events if relevant

Position persistence logic

If an order to open is submitted:
	•	create provisional position row with OPENING

If exchange confirms open:
	•	status -> OPEN

If exchange temporarily fails to return position:
	•	keep last known open position for grace window, e.g. 60–180 seconds
	•	status may become OPEN_STALE, but still counted in exposure

If close submitted:
	•	status -> CLOSING

If position disappears from exchange but settlement not yet landed:
	•	CLOSED_PENDING_SETTLEMENT

Only after settlement lands:
	•	CLOSED_SETTLED

This prevents open exposure from disappearing from portfolio.

Pseudocode

function derivePortfolioPositionValue(position) {
  if (position.status === 'OPEN' || position.status === 'OPENING' || position.status === 'REDUCING' || position.status === 'CLOSING') {
    return position.marginLocked + position.unrealizedPnl;
  }

  if (position.status === 'CLOSED_PENDING_SETTLEMENT') {
    return 0;
  }

  return 0;
}

Better status semantics

The earlier blue/yellow/green idea is good, but tie it to strict rules:

Green = verified

Confirmed by:
	•	on-chain balance or
	•	exchange position data refreshed recently

Yellow = pending

Known and expected, but not yet finalized:
	•	in transit
	•	pending settlement
	•	recently opened/closing positions
	•	stale but last-known valid positions

Red/Orange = exception

Unexplained mismatch:
	•	missing settlement
	•	unmatched outflow
	•	missing position
	•	suspected double count

Do not use blue for uncertainty if users interpret it as broken.
Use:
	•	green = verified
	•	amber = pending
	•	red = issue

Psychologically much better.
