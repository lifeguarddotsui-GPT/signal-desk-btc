Blue Water Agents — Settlement-Safe Wallet Topology

Objective

Build a wallet/accounting system where:
	•	every SUI always has a known location
	•	closed positions always return principal to agent funding
	•	rewards are split only from real realized profit
	•	“in transit” is explicit, temporary, and reversible
	•	frontend can show exact state of capital at every stage
	•	accounting drift becomes detectable, explainable, and fixable

⸻

1. Core wallet model

Each agent should have logical balances separated by purpose.

Per-agent capital buckets

type AgentLedger = {
  agentId: string

  netDeposited: number

  fundingWalletBalance: number
  savingsWalletBalance: number
  rewardsEscrowBalance: number

  openPositionCollateral: number
  reservedForOpenOrders: number
  unsettledReturns: number
  pendingInternalTransfers: number

  realizedPnl: number
  unrealizedPnl: number
  paidFees: number

  lastReconciledAt: string
}

Meaning of each bucket

1. Funding Wallet

Main deployable balance.
This is where position collateral should return after settlement.

2. Savings Wallet

Protected capital.
Never used for active collateral unless explicitly transferred.

3. Rewards Escrow

User-claimable rewards only.
Must be funded only from realized positive pnl, never from returned principal.

4. Open Position Collateral

Collateral actively tied to live positions.

5. Reserved For Open Orders

Capital temporarily locked for orders submitted but not yet filled/cancelled.

6. Unsettled Returns

Capital from positions that are closed on-chain but not yet credited back to funding wallet.

7. Pending Internal Transfers

Capital moving between internal wallets, such as funding → savings or funding → execution.

⸻

2. Never treat wallets as the source of truth alone

The source of truth must be:

economicValue =
  fundingWalletBalance +
  savingsWalletBalance +
  rewardsEscrowBalance +
  openPositionCollateral +
  reservedForOpenOrders +
  unsettledReturns +
  pendingInternalTransfers

And separately:

totalPnl =
  realizedPnl + unrealizedPnl - paidFees

3. Mandatory lifecycle states

Every position needs a durable lifecycle.

type PositionLifecycle =
  | "INTENT_CREATED"
  | "COLLATERAL_RESERVED"
  | "ORDER_SUBMITTED"
  | "OPEN"
  | "CLOSE_REQUESTED"
  | "CLOSING"
  | "CLOSED_AWAITING_SETTLEMENT"
  | "SETTLED"
  | "RETURN_CREDITED"
  | "REWARD_SPLIT_APPLIED"
  | "COMPLETE"
  | "ERROR"

Why this matters

Right now your system seems to jump from:

OPEN -> reward event

instead of:

OPEN
-> CLOSE_REQUESTED
-> CLOSING
-> CLOSED_AWAITING_SETTLEMENT
-> SETTLED
-> RETURN_CREDITED
-> REWARD_SPLIT_APPLIED
-> COMPLETE

That missing middle is where the capital disappears.

4. Correct close/settlement flow

A. Open position

When opening a position:

fundingWalletBalance -= collateral
openPositionCollateral += collateral

If order is not filled yet:

fundingWalletBalance -= reservedAmount
reservedForOpenOrders += reservedAmount

Then when filled:

reservedForOpenOrders -= collateral
openPositionCollateral += collateral


⸻

B. Close requested

When user/agent closes:

position.state = "CLOSE_REQUESTED"

When on-chain close tx lands:

position.state = "CLOSED_AWAITING_SETTLEMENT"

Do not remove economic value.
Just move it from open collateral to unsettled.

openPositionCollateral -= priorCollateralReference
unsettledReturns += expectedSettlementEstimate

If estimate is unknown, keep collateral in openPositionCollateral until actual settlement detected.

⸻

C. Settlement detected

Settlement event must capture:

interface SettlementEvent {
  positionId: string
  returnedPrincipal: number
  realizedPnl: number
  fees: number
  grossSettlementValue: number
  destinationWallet: string
  txDigest: string
  timestamp: string
}

Where:

grossSettlementValue = returnedPrincipal + realizedPnl - fees

Then:

unsettledReturns -= grossSettlementValue
fundingWalletBalance += grossSettlementValue
realizedPnl += realizedPnl
paidFees += fees

If no separate unsettled bucket was used, then at minimum:

openPositionCollateral -= returnedPrincipalReference
fundingWalletBalance += grossSettlementValue


⸻

D. Reward split applied

Only after settlement is credited to funding:

if (realizedPnl > 0) {
  const reward = realizedPnl * rewardRatio
  const reinvest = realizedPnl * reinvestRatio

  fundingWalletBalance -= reward
  rewardsEscrowBalance += reward

  // reinvest remains in funding wallet
}

That is the only legal reward path.

5. Hard invariant rules

These should run constantly.

Invariant 1 — No principal leakage

returnedPrincipal must always be credited to either:
- funding wallet
- savings wallet
- pending internal transfer

Never directly to rewards.

⸻

Invariant 2 — Rewards can only come from positive realized pnl

rewardTransfer <= max(0, realizedPnl * rewardRatio)

If violated, raise fatal error.

⸻

Invariant 3 — Closed positions cannot remain uncredited forever

If position is in:

CLOSED_AWAITING_SETTLEMENT

for longer than threshold, such as 60s or 120s:
	•	mark warning
	•	poll chain
	•	inspect execution wallet
	•	inspect destination wallet
	•	attempt recovery

⸻

Invariant 4 — System value conservation

previousEconomicValue
+ deposits
+ externalCredits
- withdrawals
- externalFees
= currentEconomicValue +/- explainablePnL

If not, drift exists.

6. Wallet topology recommendation

Use logical wallet roles, even if some are the same physical address initially.

Recommended structure

1. Agent Funding Wallet
	•	receives deposits
	•	funds positions
	•	receives settled principal back
	•	retains reinvest portion

2. Agent Savings Wallet
	•	stores non-active capital
	•	excluded from deployable buying power
	•	included in portfolio value

3. Rewards Escrow Wallet
	•	receives reward split only
	•	claimable by user
	•	never used as trading capital unless user explicitly reinvests

4. Execution Wallet or Execution Context
	•	optional
	•	can be temporary routing wallet
	•	must never be treated as lost funds
	•	must be fully reconciled

5. Transit Ledger

Not necessarily a wallet, but a table:
	•	close pending
	•	settlement pending
	•	transfer pending
	•	order reserve pending

This is what your UI is missing.

Do not derive portfolio only from current wallet RPC calls.

Maintain a ledger.

Then every UI number is explainable as a sum of ledger entries, not just flaky RPC snapshots.

8. Reconciliation engine

Build a dedicated reconciler that runs every few seconds.

Inputs
	•	on-chain wallet balances
	•	open positions from venue
	•	pending close txs
	•	reward transfer txs
	•	savings transfer txs
	•	internal ledger entries

Outputs

Reconciliation pseudocode

async function reconcileAgent(agentId: string) {
  const chain = await fetchOnchainState(agentId)
  const venue = await fetchVenuePositions(agentId)
  const ledger = await fetchLedgerState(agentId)

  const computed = computeEconomicBuckets(chain, venue, ledger)
  const stored = await fetchStoredAgentSnapshot(agentId)

  const drift = diffBuckets(computed, stored)

  if (drift.totalAbs > DRIFT_THRESHOLD) {
    await flagDrift(agentId, drift)
  }

  await saveAgentSnapshot(computed)
}

9. Settlement recovery worker

This is the worker you urgently need.

Job

For all positions in:
	•	CLOSING
	•	CLOSED_AWAITING_SETTLEMENT
	•	SETTLED but not RETURN_CREDITED

poll chain and recover missing capital path.

Pseudocode

async function settlementRecoveryWorker() {
  const stuck = await getStuckPositions()

  for (const pos of stuck) {
    const closeTx = await fetchCloseTx(pos.closeTxDigest)
    const settlement = await fetchSettlementEvent(pos.positionId)
    const executionWalletFlows = await fetchExecutionWalletFlows(pos.positionId)

    if (settlement) {
      await applySettlement(pos, settlement)
      continue
    }

    if (executionWalletFlows.fundsArrivedButNotCredited) {
      await createRecoveryLedgerEntries(pos, executionWalletFlows)
      await creditFundingWalletFromRecovery(pos, executionWalletFlows.amount)
      continue
    }

    await markPositionWarning(pos.id, "Settlement unresolved")
  }
}
