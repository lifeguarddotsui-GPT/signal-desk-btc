## What the development build now does

- Validates WaterX current/neighbor round identities and prefers an actually active round over a future preview. Retains prospective first observations, bounded settlement retry, first-seen/accepted-label timestamps, source evidence and revisions. Contradictory valid settlement revisions are explicitly disputed and excluded from evaluation without erasing original evidence. Rejected evidence can be corrected later. These are internal consistency checks over WaterX's report, **not** independent Chainlink TWAP verification.
- Keeps BTC 5m and 15m isolated. The desk is advisory and HOLD-only: no wallet custody, order, fill, or executable quote. Displayed $5 arithmetic is indicative gross from provider odds, before unknown fees/gas, not a net-return claim.
- Provides a compact mobile-oriented chart-first layout with Coinbase **comparison-only** price observations, interval-specific round/rolling windows, gaps, source labeling, measured container sizing, inspection and return-to-live. No WaterX price trace or inferred settlement is invented. A final desktop capture is at `screenshots/waterx-desktop-final.jpg`; 320/375/390/430 phone captures were not reliably obtained from headless Chromium in this environment. Do not mark phone visual acceptance complete until captured on devices.
- Adds `/api/waterx/latency?interval=5|15` with per-stage count, p50/p95/p99 and observation bounds for archived Coinbase source timestamp→server receipt, process-local receipt→publish, WaterX round start→first stored observation and reported settlement→accepted label. The live browser measures receipt→first chart animation frame in the current tab only. Publish→browser network delay is **unavailable** because a verified cross-device clock offset is absent. A rounded 0ms publish measure is not zero network delay.
- Captures an immutable prospective feature snapshot only when a confirmed WaterX anchor, identical first-frozen odds observation, and complete pre-decision Coinbase source-stamped three-minute tick lookback exist. The odds timestamp is the app's observation time; the provider does not supply an odds creation timestamp. A separate offline candidate trainer uses strictly chronological train/calibration/untouched-test partitions and same-round market baselines, stores immutable attempts, and never promotes. The Learning view shows the latest read-only candidate attempt separately from the market baseline. The current development training run reported **zero** eligible feature snapshots for both intervals and `promoted:false`; this is no evidence of improvement or forecast readiness.
- Provides a separate database-leased collector entrypoint and manual offline training command. Merely having this code does not schedule the worker or make autoscale production always-on.

## Proposed gated rollout / recovery

1. Verify a restorable production database backup and approve the additive schema change (including its outcome-check replacement) through the supported publish/migration flow. Do not run startup DDL or overwrite production data.
2. Obtain approval for an always-on target and its operating cost, provision the independent worker against the intended persistent database, verify its database lease and graceful restart, and set `WATERX_EXTERNAL_COLLECTOR=true` on the web process **only after** the worker is independently observed. Keep the web request-time refresh as a bounded fallback. Do not set the flag without a working collector.
3. Observe both intervals over full rounds, reconnects and settlement delays; sample latency windows on actual phones, inspect provider changes, and verify 5m/15m public endpoints and chart behavior. Do not promote a candidate without sufficient prospective evidence and separate review.
4. If collection fails, remove the external-collector flag so web-process collection resumes where supported, stop the worker, and roll back the application build via an approved checkpoint/deployment. Preserve additive evidence and disputed labels; do not delete history as a rollback. If schema compatibility differs in production, halt the rollout rather than inventing an in-process migration.

**Status:** tested development build; **not released to production**. Always-on operation, production backup/schema safety, phone acceptance and multi-round evidence are outstanding gates.
