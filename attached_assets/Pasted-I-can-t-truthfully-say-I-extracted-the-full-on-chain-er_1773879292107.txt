Most likely settlement-logic error

The agent is probably doing this:
	1.	Detects an open position.
	2.	Tries to close it.
	3.	Does not mark that position as closing_pending.
	4.	Fails to verify whether a prior close tx is already in flight or whether the position is already reduced/closed on-chain.
	5.	Re-attempts close on every loop tick.
	6.	Each failed attempt burns gas from the funding wallet.

So the real bug is likely:

No idempotency + no in-flight lock + no reconciliation-before-retry.

That matches your symptom exactly: “agent keeps failing to close open position” and “gas to close it is draining my funding wallet.”

What the Replit agent should fix

Tell the Replit agent to implement this exactly:

1) Add a position lifecycle state machine

Every tracked position must have one of these states:
	•	open
	•	close_requested
	•	closing_pending
	•	closed
	•	close_failed_retryable
	•	close_failed_terminal

Rules:
	•	Once a close tx is submitted, immediately move the position to closing_pending.
	•	While closing_pending, block any new close attempt for that same position.
	•	Only leave closing_pending after:
	•	confirmed success on chain, or
	•	explicit confirmed failure + post-failure reconciliation.

2) Add a hard in-flight close lock

Before sending a close tx, acquire a lock keyed by:
	•	agent_id
	•	market
	•	position_id

Example key:
close-lock:${agentId}:${market}:${positionId}

Rules:
	•	TTL: 60–120 seconds
	•	If lock exists, skip close attempt
	•	Lock released only after tx finalization or timeout + reconciliation

This prevents loop spam and duplicate closes.

3) Reconcile on-chain position state before every retry

Before retrying any failed close:
	•	Fetch current on-chain position size
	•	Fetch current open orders for that market
	•	Fetch last submitted close tx digest for this position
	•	Check if size is already 0 or materially reduced

If size is already zero:
	•	mark closed
	•	stop retrying
	•	never spend more gas

If size changed:
	•	update local record
	•	compute remaining size
	•	only close the remainder

4) Store close intent and tx digest persistently

The bug is often caused by memory-only tracking. Persist this in DB:
	•	position_id
	•	close_requested_at
	•	last_close_tx_digest
	•	last_close_attempt_at
	•	last_close_error
	•	close_attempt_count
	•	last_known_onchain_size

On restart, the agent must resume from DB state, not “forget” and fire another close.

5) Dry-run every close before broadcasting

Use dry-run first for every close payload to catch:
	•	stale object/version
	•	invalid position args
	•	insufficient gas budget
	•	already-closed/no-position cases
	•	slippage / oracle / protocol aborts

If dry-run fails:
	•	do not broadcast
	•	save the dry-run error
	•	classify it:
	•	retryable
	•	terminal

This is critical because dry-run can reveal exact execution failure before you waste gas on-chain.  ￼

6) Distinguish retryable vs terminal close errors

Implement classifier:

Terminal errors → stop retrying
	•	position not found
	•	position size already zero
	•	invalid arguments
	•	stale local position id that no longer exists
	•	already settled/already closed semantic failures

Retryable errors
	•	RPC timeout
	•	temporary shared object contention
	•	transient oracle unavailability
	•	temporary gas coin selection failure

For terminal errors:
	•	mark close_failed_terminal
	•	trigger full reconciliation
	•	do not auto-retry

For retryable errors:
	•	exponential backoff:
	•	10s
	•	30s
	•	60s
	•	120s
	•	max 3–5 retries

7) Never use the whole funding wallet as the active gas source

Reserve a protected gas bucket.

Example:
	•	trading_capital
	•	gas_reserve
	•	rewards_bucket

Rules:
	•	Gas reserve fixed minimum, e.g. 0.5–1.5 SUI
	•	If retries exceed threshold, halt close automation and alert instead of draining capital
	•	Never let automated retries consume below the configured floor

8) Add duplicate-intent protection in the scheduler

Your monitor loop should not do:

if position.open -> close()

It should do:

if position.open and no close intent and no in-flight tx -> request close

After that, a separate close executor handles the request once.

So split into:
	•	detector
	•	intent writer
	•	executor
	•	reconciler

Not one loop doing everything.

9) Treat “submitted tx but unknown outcome” as a special case

If RPC returns ambiguous status or timeout after submission:
	•	do not re-send immediately
	•	first query the tx digest
	•	then query live on-chain position state
	•	only retry if both confirm no effect occurred

This is where many bots double-close or repeatedly attempt close.

10) Add settlement routing validation after close success

Once close succeeds:
	•	verify proceeds destination
	•	verify balance delta on:
	•	agent main wallet
	•	funding wallet
	•	savings wallet
	•	persist a settlement_record

Fields:
	•	source_position_id
	•	close_tx_digest
	•	realized_pnl
	•	returned_collateral
	•	gas_spent
	•	destination_wallet
	•	settlement_status

If destination != expected funding wallet, flag settlement_misroute.
