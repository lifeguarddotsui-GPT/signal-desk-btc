Here’s the update plan I’d pass to the Replit agent.

The core problem is not just “frontend latency.” It’s that the system still does not have a strong portfolio state machine or a canonical ledger for order/position lifecycle. Because of that:
	1.	the UI loads partial truth,
	2.	agent balances drift from Typus settlement reality,
	3.	open positions disappear or lag,
	4.	“in transit” is not modeled rigorously,
	5.	SL/TP monitoring likely misses state transitions during RPC lag / indexer lag / reconnect windows.

What you need is a backend-first reconciliation architecture, not more frontend polling.

⸻

1. Main diagnosis

Current failure pattern

From the screenshots and your description, there are a few likely root causes happening at once:

A. Position lifecycle is not pinned end-to-end

Open positions are probably being derived from current live RPC snapshots instead of being tracked as durable entities from:
	•	order submitted
	•	order accepted
	•	fill opened
	•	position live
	•	reduce/close requested
	•	close pending
	•	settled
	•	collateral returned

That causes positions to temporarily vanish, duplicate, or show null while the system waits for chain/indexer confirmation.

B. No true “fund flow ledger”

Your UI card is trying to infer economic value from scattered sources:
	•	funding wallet
	•	agent savings wallet
	•	open positions
	•	unsettled settlements
	•	claimable rewards
	•	closing proceeds
	•	keeper settlement / Typus return flow

Without a canonical flow ledger, “wallets + rewards + maybe positions” will never equal reality consistently.

C. Frontend is reading before reconciliation completes

The page is loading before the backend has:
	•	fetched wallet balances
	•	resolved open positions
	•	resolved pending closes
	•	resolved in-transit transfers
	•	matched settlement returns to originating agent

So users see partial truth first, then slow corrections.

D. Execution agent is probably coupled too tightly to stale reads

If the execution loop uses the same laggy state source as the UI, then SL/TP decisions may be made off stale or incomplete data. That can explain:
	•	oversized losses
	•	visible liquidations
	•	missed stop closes
	•	duplicate close attempts
	•	late close attempts

E. Agent balance is likely being computed as “wallet balance only”

If Typus settlement has returned funds but they are not yet reconciled into the agent’s accounting bucket, the UI can show lower agent value than actual lifecycle value.

2. Highest-priority architecture change

Build one canonical backend “Portfolio Reconciliation Engine”

Replit agent should stop treating the frontend as a live calculator.

Instead create a backend service that continuously computes and stores canonical state for:
	•	user portfolio
	•	per-agent portfolio
	•	per-position lifecycle
	•	per-order lifecycle
	•	transfer lifecycle
	•	settlement lifecycle

The frontend should read this precomputed canonical state, not raw fragmented data.

4. Backend services to add

A. execution-service

This is the agent brain. It should place/manage orders only.

Responsibilities:
	•	receive trading signal
	•	place entry
	•	register order intent
	•	register SL/TP immediately
	•	detect close triggers
	•	submit close intent
	•	never compute UI portfolio totals

It should write to journals, not directly drive UI.

⸻

B. position-tracker-service

Continuous watcher for real position status.

Responsibilities:
	•	read Typus / onchain / indexer state
	•	map exchange positions to internal position_journal
	•	update LIVE / CLOSE_CONFIRMED / LIQUIDATED / SETTLEMENT_PENDING
	•	maintain per-position heartbeat timestamp

This keeps open positions pinned even during partial failures.

⸻

C. settlement-reconciler-service

This is the missing piece for agent balances.

Responsibilities:
	•	detect collateral returned after close
	•	detect settlement proceeds arrival
	•	detect savings transfers
	•	match proceeds back to originating position and agent
	•	post final ledger events
	•	mark SETTLED

This should be the source of truth for the agent balance card.

⸻

D. portfolio-aggregator-service

This computes frontend-ready snapshots.

Responsibilities:
	•	user wallet card snapshot
	•	per-agent snapshot
	•	accounting health %
	•	unresolved reconciliation count
	•	freshness timestamps
	•	confidence levels

The frontend should load from this snapshot API, not from 8 independent live calls.

⸻

E. rpc-health-router

Likely needed if latency is high.

Responsibilities:
	•	maintain pool of RPC/indexer providers
	•	score endpoints by latency / freshness / errors
	•	fail over automatically
	•	separate write path from read path

Writes should use the most reliable endpoint.
Reads should prefer fastest verified source, but reconciler should confirm from multiple sources before finalization.

5. Fix the execution agent specifically

A. Separate “decision state” from “display state”

Execution must not depend on the same delayed aggregate state the UI uses.

Execution should use a dedicated internal state:
	•	latest confirmed live positions
	•	latest working orders
	•	latest stops/tps registered
	•	risk lock state
	•	cooldown state
	•	agent free collateral
	•	max exposure
	•	pending close intents

UI can lag a few seconds. Execution cannot.

⸻

B. Introduce a risk-lock before entry and during close

When entry or close is in-flight, set temporary locks so the agent does not:
	•	double-enter
	•	over-allocate collateral
	•	attempt duplicate closes
	•	think closed collateral is already reusable before settlement

Suggested locks:
	•	ENTRY_LOCK
	•	CLOSE_LOCK
	•	SETTLEMENT_LOCK
	•	EMERGENCY_HALT

Add fields:
	•	sl_registered
	•	tp_registered
	•	sl_verified_at
	•	tp_verified_at

Status examples:
	•	PROTECTED

11. SL/TP reliability changes

Tell the Replit agent to implement this exact policy:

On entry:
	1.	submit entry intent
	2.	wait for entry confirmation
	3.	immediately submit SL + TP protection
	4.	verify SL + TP existence
	5.	only then mark position as PROTECTED

During live position:
	1.	poll/subscribe for mark price
	2.	verify stop/tp integrity each cycle
	3.	if protection missing, re-arm once
	4.	if re-arm fails and risk threshold breached, emergency close
	5.	set EMERGENCY_HALT on repeated failures

On close:
	1.	mark CLOSE_REQUESTED
	2.	submit close
	3.	keep position pinned as CLOSE_SUBMITTED
	4.	when close confirmed, move to SETTLEMENT_PENDING
	5.	only after funds are reconciled, mark fully SETTLED

This prevents the current situation where position disappears before funds return.
